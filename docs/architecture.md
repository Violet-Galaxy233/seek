# Seek 架构说明

## 当前架构

```text
MusicBrainz API ──→ SQLite 专辑/发行版/曲目
                         ↑
Cover Art Archive ──→ data/covers/ 封面缓存
                         ↓
              本地 Qwen3-VL 图片编码
                         ↓
     向量缓存 + FAISS 索引 + 索引清单
                         ↑
中文模糊描述 → 本地 Qwen3-VL 文本编码
                         ↓
                Top-K 相似封面检索
                         ↓
            FastAPI JSON / Gradio 网格
```

导入是当前唯一联网阶段。查询和索引在本地运行。启动时比较模型标识、向量维数和封面 SHA-256；数据未变化时复用索引，有差异时只编码新增或变化图片，再原子替换 FAISS、清单和向量缓存。

## 目标参赛架构

```text
微信小程序
  ├── 模糊记忆输入
  ├── 候选封面网格
  ├── 三态主动追问
  └── 专辑与曲目确认
          │ HTTPS
          ▼
API 服务
  ├── 输入校验、匿名会话、限流
  ├── MemoryClue 解析
  ├── 多路召回与候选融合
  ├── 主动问题选择
  └── 解释和反馈记录
          │
          ├── 文本向量服务：常驻 Qwen 模型
          ├── 向量索引：封面、元数据、歌曲
          ├── 全文索引：名称、别名、OCR
          ├── 关系数据库：音乐实体和来源
          └── 对象存储/CDN：封面缩略图

离线数据管线
  数据转储/授权数据源
    → 规范化与去重
    → 视觉分析和元数据补全
    → 批量计算向量
    → 自动评测
    → 生成版本化索引
    → 原子发布
```

小程序不能加载 4 GB 模型，也不能访问开发机的 localhost。封面向量必须离线预计算；线上每次查询只计算用户文字向量并检索已有索引。

## 模块边界

- `app.domain`：领域对象，不依赖 API、数据库或模型。
- `app.ports`：向量提供者和仓库接口。
- `app.adapters.sqlite_repository`：当前真实数据仓库。
- `app.adapters.musicbrainz`：MusicBrainz/CAA 小规模导入与兼容下载。
- `app.adapters.qwen_vl`：本地 Qwen 图文编码。
- `app.adapters.faiss_index`：持久化、增量缓存和查询。
- `app.indexed_search`：当前单路封面检索。
- `app.search`：假数据上的记忆回答和问题选择原型。
- `app.runtime`：组装模型、仓库和索引。
- `app.api`：FastAPI 协议边界。
- `app.ui`：Gradio 验证页，不是最终小程序界面。
- `app.adapters.file_catalog`、`memory` 和 `fixtures`：快速测试基线。

后续新增数据库、云存储和模型服务时必须通过端口接入，不能把 SDK 调用散布到业务层。

## 目标领域模型

### Artist

- MBID 或其他稳定来源 ID
- 主名称、别名、不同文字和译名
- 人物、乐队、组合、管弦乐团等类型
- 出生/成立地区与主要活动地区
- 活跃年代

不要从名称、照片或演唱语言推断种族。公开数据中的地区也只作为带来源的事实。

### ReleaseGroup / Album

- 抽象音乐作品集合
- 标题与别名
- Album、EP、Single、Soundtrack 等类型
- 首发时间
- 艺人关系
- 多标签曲风

### Release

- 具体国家、日期、唱片公司、条码和状态
- 关联 ReleaseGroup
- 一个或多个具体封面

### Recording / Track

- 录音实体与具体发行版曲目
- 名称、别名、艺人、时长
- 演唱语言、是否纯音乐、人声类型
- 曲风、作品和动画/影视/游戏等关系

### Cover / CoverAnalysis

- 原图和缩略图来源、哈希、尺寸、许可与下架状态
- 图像向量和模型版本
- 主色及占比、物体和数量、人物、人脸、OCR
- 摄影/插画/拼贴、明暗、构图和 AI 描述
- 每项分析结果的置信度和来源

### MemoryClue

- 原始用户表达
- 类型、规范化值和时间范围
- 正向/负向极性
- 用户确定程度和系统解析可信度
- 用户是否确认
- 来源：原始描述、追问或系统推断

原始记忆必须原样保留；规范化结果单独存储。

## 混合检索

目标系统至少包含四条召回路线：

1. 封面视觉向量：物体、颜色、构图和风格。
2. 元数据语义向量：艺人、语言、地区、曲风、年代和类型。
3. 全文搜索：标题、译名、罗马字、艺人别名和 OCR。
4. 结构化条件：语言、发行时间、地区、是否纯音乐等。

候选集合合并后按动态权重重排：

```text
score =
  visual_similarity * visual_confidence
  + metadata_similarity * semantic_confidence
  + lexical_match
  + genre/language/era evidence
  - confirmed_conflict_penalty
```

低置信度冲突只应轻微降权，只有用户明确确认的冲突才能大幅惩罚。相似度不是答案概率。

## 主动追问

问题不应只来自固定顺序。系统应比较当前 Top-K 候选属性，选择预期信息增益最大的一个问题，例如“封面上有人吗”能将候选近似分成两组时优先提问。每轮只问一个问题，三态回答分别处理，支持撤销。

## 模型和索引

- 当前默认模型：`Qwen/Qwen3-VL-Embedding-2B`。
- 当前完整维数：2048，图片处理上限 512×512。
- 当前设备优先级：MPS、CUDA、CPU。
- 当前小规模索引：归一化向量 + FAISS `IndexFlatIP`。
- 扩大后可用压缩向量进行第一阶段召回，再用完整向量和结构化证据重排。
- 每个索引版本必须记录模型、维数、数据快照、构建时间和质量报告。
- Web 进程不得直接修改线上索引；发布新版本时原子切换并保留回滚版本。

## 数据库和部署

- 本地开发继续使用 SQLite。
- 服务器版本优先采用 PostgreSQL 存储音乐实体、来源、会话和反馈。
- FAISS 可以作为独立只读索引文件挂载到查询服务。
- Qwen 作为常驻单实例或独立向量服务加载，避免每个 API worker 重复占用显存。
- 封面放入对象存储/CDN，小程序只请求压缩缩略图。
- 公网服务必须使用 HTTPS、合法域名、限流、超时、健康检查和日志脱敏。

## 隐私、版权和失败处理

### 隐私

- 参赛 MVP 不要求登录，使用短期匿名会话。
- 明确说明查询和反馈是否保存、保存多久及用途。
- 默认不长期保留原始查询；评测样本需单独征得同意并去标识化。

### 版权和来源

- MusicBrainz 核心转储和派生标签具有不同许可，必须分别记录。
- Cover Art Archive 公开访问不等于获得全部公开展示或商业使用权。
- 每张封面保存来源和下架状态，支持权利人请求后立即下架。
- 公开比赛版本的数据源与授权策略见 `docs/data-strategy.md`。
- 不下载或存储完整音频。

### 失败处理

- 模型、数据库或索引缺失时返回明确错误，不静默调用外部 API。
- 查询超时、排队、网络失败、空结果和封面加载失败必须有独立 UI 状态。
- 没有足够证据或答案不在目录时明确说明，不生成伪候选。
- 相同分数使用稳定实体 ID 排序。
